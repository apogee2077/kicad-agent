# 提示词工程与架构调研

> 调研时间：2026-11-20
> 目的：为 W3–W4「让模型稳定产出可用连接关系」寻找可借鉴的做法
> 触发原因：真实模型连续两次把 LED 与限流电阻接错（`GPIO—电阻—GND`、
> LED 阳极悬空），且**重试无法纠正** —— 这是概念性错误，不是格式错误

## 2. 最关键的发现：CircuitAgent 的「积木」思想

原文（中文，来自其 PyPI 页面）：

> 让大语言模型直接生成底层走线、焊盘与封装，**几乎必然产出非法几何或引脚短路**。
> CircuitAgent 的做法是把 LLM 的输出**约束在预验证的电路积木上**，
> 再用 Pydantic 契约把它变成确定性网表 ——
> **模型只负责「选积木」，不负责「画线」**。

它的积木清单里，正好有我们失败的那一项：

| 积木 | 说明 | 关键设计点 |
| --- | --- | --- |
| `block_led` | 状态指示灯 | **限流电阻 + 颜色/阻值可参数化** |
| `block_button` | 消抖按键 | 10k 上拉 + 100nF RC |
| `block_power_ldo_3v3` | AMS1117-3.3V | 10µF 输入/输出储能电容 |
| `block_i2c_header` | I2C 扩展排针 | SCL/SDA 各 4.7k 上拉 |

**这解释了我们的失败**：我们是让模型「从零画连线」，它必须自己知道
「电阻要和 LED 串联」这条拓扑知识；一旦这条知识不牢，就产出
`GPIO—电阻—GND` + `LED 阳极悬空` 这种局部合理、整体错误的接法。

如果提供 `block_led(gpio=IO25, color=Red, r=220)` 这样的积木，
模型只需**选积木 + 填参数**，拓扑由积木保证，这类错误从根上不可能发生。

它的其它可取之处：

- **确定性**：同一句话永远产出逐字节相同的结果（CI 有断言）
- **每个积木有单测**：位号唯一、元件都有封装与料号、网络端点必须指向已声明元件、每个积木必须接 GND
- **`unmatched` 字段**：未识别的意图单独返回，**不被静默丢弃**
- **契约即 SSOT**：Pydantic / JSON Schema 是唯一事实来源

## 3. 我们已有的做法 vs 最佳实践

| 最佳实践 | 我们现状 |
| --- | --- |
| schema-first（先定契约） | ✅ `schema.py` 分 BomStage / ConnectionStage / Design |
| 生成 → 校验 → 修复循环 | ✅ `call_with_retry`，最多 3 次 |
| 多层校验：语法 / Schema / 业务规则 | ✅ 语法（`extract_json`）+ schema（pydantic）+ 业务（`check_design`） |
| 用真实事实喂模型，不靠记忆 | ✅ 注入 KiCad 符号库实时查出的引脚表（这一点我们做得比多数方案好） |
| 确定性解码 `temperature=0` | ❌ 现在是 `0.2` |
| 结构化输出（`response_format`） | ❌ 目前仅靠提示词约束 |
| **积木化 / 预验证子电路** | ❌ **完全没有 —— 这是最大的缺口** |
| 未识别意图显式上报 | ❌ 没有 `unmatched` 字段 |
| 分块生成 | ❌ 一次生成整板 |
| 积木级单元测试 | ❌ 无 |

## 4. 结论与建议

### 判断

我们的**校验层已经达标**（schema + 业务规则 + 重试回灌），
但**生成层是"裸奔"的**：把「怎么连线」这件专业工作整个丢给模型。

重试只能纠正**格式**问题（单节点网络、短路、漏接），
纠正不了**拓扑**问题（电阻与 LED 怎么串）——已经被两次实测证实。

### 建议的改进优先级

| # | 改进 | 依据 | 预期收益 |
| --- | --- | --- | --- |
| 1 | **引入积木层**：`block_led` / `block_ldo` / `block_button` / `block_i2c` 等预验证子电路 | CircuitAgent | 从根上消除拓扑错误 |
| 2 | `temperature=0` | JSON prompting 实践 | 提高确定性，便于复现与对比 |
| 3 | 尝试 `response_format={"type": "json_object"}` | 同上 | 减少围栏与废话，降低重试率 |
| 4 | 增加 `unmatched` 字段 | CircuitAgent | 需求没被满足时能看见，不被静默丢弃 |
| 5 | 分块生成 | CircuitAgent 的"小积木集"哲学 | 降低单次任务复杂度 |

### 对报告的意义

这条调研链可以写成报告里的「相关工作 + 方案演进」：

> 初始方案让模型直接生成引脚级连线 → 实测出现拓扑性错误且重试无效
> → 调研同类系统 → 发现业界主流做法是「约束在预验证积木上，
> 模型只选积木不画线」→ 据此改造架构。

比单纯说"我们用了大模型"有说服力得多。
